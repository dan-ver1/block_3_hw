# Домашнє завдання 3: Weekly Learning Health Report

Я зібрав у n8n звіт про навчальну активність на демонстраційній вибірці з 15 `enrollments`, а не на всій базі. Через PostgreSQL я отримую агреговані дані, у двох Code-вузлах визначаю статуси й рахую метрики. Gemini формує короткий управлінський підсумок; результат я записую в Google Sheets.

## Як працює workflow

```text
Manual Trigger ────┐
                   ├→ PostgreSQL → Code: статуси → Code: метрики → Gemini → Google Sheets
Schedule Trigger ──┘
```

У SQL я групую записи `weekly_activity` за `enrollment_id`. Для кожного запису я рахую переглянуті хвилини, середній `quiz_score`, кількість спроб пройти тест та активних тижнів. Запит бере по 5 `enrollments` із трьох груп: з одним рядком активності, з 2–4 рядками та з 5 або більше рядками. Отже, 15 — заданий розмір демонстраційної вибірки, а не загальна кількість записів у базі. У першому Code-вузлі я застосовую правила нижче. У другому рахую показники для звіту. Я передаю Gemini один набір підсумкових метрик і роблю один виклик моделі на звіт.

## Правила статусів

У Code-вузлі я перевіряю умови в цьому порядку:

1. **`inactive`**: `last_active_week <= 1`. У вибірці немає запису про продовження навчання після першого тижня. За цим правилом не можна встановити, чи студент активний зараз.
2. **`needs_attention`**: активність після першого тижня є, але `active_weeks < 5`, або середній перегляд за активний тиждень менший за 30 хвилин, або `avg_quiz_score < 70`.
3. **`healthy`**: жодна з попередніх умов не спрацювала. Запис має щонайменше 5 активних тижнів, не менше 30 хвилин перегляду за активний тиждень і середній бал quiz від 70.

Я обрав пороги для цього ДЗ. Вони не є навчальними нормативами. Gemini не бере участі у визначенні статусу.

## Структура звіту в Google Sheets

Кожен запуск додає один рядок із такими стовпцями:

| Стовпець | Що означає |
| --- | --- |
| `run_date` | Дата запуску workflow за київським часом; це не дата навчальної активності. |
| `n_enrollments` | Кількість проаналізованих `enrollment_id` у вибірці; це не кількість унікальних студентів. |
| `healthy_count` | Кількість записів зі статусом `healthy`. |
| `needs_attention_count` | Кількість записів зі статусом `needs_attention`. |
| `inactive_count` | Кількість записів зі статусом `inactive`. |
| `avg_quiz_score` | Середнє арифметичне від середніх балів quiz для відібраних `enrollments`; кожен запис має однакову вагу. |
| `summary` | Короткий управлінський підсумок, який Gemini створює з переданих загальних метрик. |

Повторні тести створили кілька рядків з датою `2026-10-11`. Це окремі запуски на тій самій демонстраційній вибірці, а не звіти за різні тижні.

## Бонус: запуск раз на тиждень

Я налаштував Schedule Trigger на понеділок о 09:00 за `Europe/Kyiv` та опублікував workflow. Я перевірив ручну гілку та гілку Schedule Trigger окремими тестовими запусками. Перший запуск за календарем ще не перевіряв. У призначений час локальний n8n має працювати.

Розклад запускає звіт щотижня, але SQL не обмежує дані останнім тижнем. Джерело містить історичну активність за 2021–2023 роки, тому цей варіант не показує поточний стан студентів. Якщо дані не зміняться, наступний запуск повторить ті самі метрики вибірки.
